# Dyar Brain — الموزّع الذكي (AI Dispatcher)

الهدف: **Dyar Brain يدير العمليات والطلبات والموصلين بنفسه** — يستقبل الطلب الجديد، يختار أقرب موصل مناسب،
يكلمه صوتيًا عبر اللاسلكي، يأخذ قبوله أو رفضه، ويتابع الطلب حتى الإغلاق. المشرف البشري يراقب ويتدخل عند الحاجة فقط.

---

## 1. الدورة الكاملة (Order → Voice → Delivery)

```
 طلب جديد من المطعم/التطبيق
          │
          ▼
 ┌─────────────────────┐
 │ 1. الترشيح          │  استبعاد: غير متصل، في طوارئ، بطارية < 15%،
 │    (Filtering)      │  خارج نطاق المنطقة، وصل حدّه الأقصى من الطلبات
 └─────────┬───────────┘
           ▼
 ┌─────────────────────┐
 │ 2. الترتيب          │  Score لكل موصل مرشح (§2)
 │    (Scoring)        │  الأقرب زمنيًا وليس فقط مسافةً
 └─────────┬───────────┘
           ▼
 ┌─────────────────────┐
 │ 3. النداء الصوتي    │  TTS عبر قناة خاصة أو نداء مباشر:
 │    (Radio Offer)    │  «محمد، طلب جديد من مطعم الشام إلى دير الأسد،
 └─────────┬───────────┘   استلام خلال 12 دقيقة — هل تقبل؟»
           ▼
 ┌─────────────────────┐   قبول: «نعم / قبلت / ماشي» أو ضغطة PTT قصيرة ×1
 │ 4. الرد             │   رفض:  «لا / مشغول»            أو ضغطة PTT ×2
 │    (STT + Intent)   │   صمت 20 ثانية = رفض ضمني ← الانتقال للتالي
 └─────────┬───────────┘
     قبول ─┤─ رفض/صمت ← عرض على المرشح التالي (حتى 3 مرشحين)
           ▼                    │ فشل الثلاثة ← تصعيد للمشرف فورًا
 ┌─────────────────────┐
 │ 5. الإسناد والتتبع  │  تحديث الطلب، فتح قناة ORDER-xxxxx،
 │    (Assign+Monitor) │  مراقبة GPS مقابل ETA، اكتشاف التأخير آليًا
 └─────────┬───────────┘
           ▼
 ┌─────────────────────┐
 │ 6. الإغلاق          │  تأكيد تسليم ← أرشفة القناة + تسجيل زمن كل مرحلة
 └─────────────────────┘
```

كل خطوة تُسجَّل في `audit_log` باسم `ai-dispatcher` — المشرف يرى القرار وسببه ويستطيع نقضه بضغطة واحدة.

## 2. اختيار «أقرب موصل» — المعادلة

الأقرب ليس أقصر مسافة هوائية، بل **أقل زمن وصول فعلي مع عدالة توزيع**:

```
Score = w1 · ETA_للمطعم        (مسار طريق فعلي OSRM، ليس خط مستقيم)
      + w2 · الحمل الحالي       (عدد الطلبات النشطة على الموصل)
      + w3 · اتجاه الحركة       (موصل متجه أصلًا نحو المطعم يتقدم)
      + w4 · عدالة التوزيع      (من لم يستلم طلبًا منذ مدة يتقدم)
      - w5 · عقوبات             (بطارية ضعيفة، شبكة ●○○○، رفض متكرر اليوم)
```

- حساب المسار والزمن: **OSRM** أو **Valhalla** (مفتوحا المصدر، يعملان على خرائط OSM محليًا — بدون Google وبدون رسوم).
- الأوزان `w1..w5` قابلة للضبط من لوحة التحكم (شاشة الإعدادات)، وتُحسَّن لاحقًا من البيانات الفعلية.
- المعادلة شفافة: بطاقة كل إسناد في اللوحة تعرض «لماذا اختير هذا الموصل» بالأرقام.

## 3. الحوار الصوتي عبر اللاسلكي

### مسار الصوت
```
نص القرار ─► TTS عربي (Piper — محلي ومجاني) ─► بث في قناة الموصل (LiveKit)
رد الموصل ─► تسجيل ─► faster-whisper (STT محلي) ─► تحليل النية ─► فعل
```

### لغة النداء (أمثلة مضبوطة)
| الموقف | ما يقوله Dyar Brain |
|---|---|
| عرض طلب | «محمد، طلب جديد: مطعم الشام إلى دير الأسد، المسافة 4 كم، الاستلام خلال 12 دقيقة. اضغط مرة للقبول أو قل نعم.» |
| تأكيد الإسناد | «تم. الطلب 18291 لك، تفاصيله على الشاشة. بالسلامة.» |
| الموصل أبلغ تأخيرًا | «سجلت تأخير عشر دقائق للطلب 18291 وأبلغت الزبون.» |
| اكتشاف تأخير من GPS | «محمد، مضى على الاستلام 15 دقيقة والمسار متوقف — هل كل شيء تمام؟» |
| تصعيد | «العمليات: الطلب 18310 رفضه ثلاثة موصلين، أحتاج قرارًا بشريًا.» |

### قواعد صارمة للرد الصوتي
- **القبول بوسيلتين دائمًا**: كلمة («نعم/قبلت/ماشي») **أو** ضغطة PTT قصيرة واحدة — لأن السائق يقود ويداه مشغولتان، وضجيج الشارع قد يفسد التعرف الصوتي.
- عتبة ثقة STT: إن كان التعرف أقل من 80% ثقة ← يعيد Brain السؤال بصيغة نعم/لا بسيطة، ولا يخمّن أبدًا.
- أي كلمة من قاموس الخطر («حادث، اصطدام، ساعدوني») في أي رد ← تحويل فوري لمسار الطوارئ P3 بغض النظر عن سياق الحوار.
- الموصل يستطيع دائمًا قول «عمليات» ← يحوّله Brain فورًا لإنسان.

## 4. حدود صلاحية الآلة (Human-in-the-loop)

| القرار | من يتخذه |
|---|---|
| إسناد طلب عادي لأقرب موصل | Brain تلقائيًا |
| تحديث ETA وإبلاغ الزبون بتأخير ≤ 15 دقيقة | Brain تلقائيًا |
| إلغاء طلب، تأخير > 15 دقيقة، خصم/تعويض | تصعيد للمشرف |
| 3 رفضات لطلب واحد | تصعيد للمشرف |
| أي إشارة طوارئ | بشري فورًا + بروتوكول P3 |
| نقض أي قرار آلي | زر «تدخّل» في اللوحة — يسحب الطلب من Brain لهذا الطلب |

وضع التشغيل قابل للتدرج من اللوحة:
1. **مراقب** — Brain يقترح فقط والمشرف ينفذ (الأسابيع الأولى).
2. **مساعد** — Brain ينفذ والمشرف يؤكد بضغطة.
3. **آلي** — Brain ينفذ ويُعلم، والمشرف يتدخل استثناءً (الوضع المستهدف).

## 5. الإضافات على قاعدة البيانات

```sql
dispatch_offers(id, order_id, driver_id, rank, score, eta_s, distance_m,
                offered_at, answered_at, answer{accept,reject,timeout}, answer_via{voice,ptt,screen})
dispatch_policies(id, weights jsonb, max_offers int, offer_timeout_s int,
                  auto_mode{monitor,assist,auto}, updated_by, updated_at)
brain_actions(id, kind, order_id, driver_id, reason text, confidence,
              reverted_by, at)          -- كل فعل آلي وسبب اتخاذه، قابل للنقض
```

`dispatch_offers` هو ذهب التحليلات لاحقًا: منه نعرف معدلات القبول لكل موصل ومنطقة وساعة، ونحسّن الأوزان.

## 6. شاشة «الموزّع الذكي» في لوحة التحكم

انظر النموذج التفاعلي (قسم «الموزّع الذكي» — فيه زر محاكاة طلب كامل):

- **طابور الطلبات الحية**: كل طلب وحالته (يُرشَّح، يُعرَض على محمد، مُسنَد، متأخر…).
- **بطاقة القرار**: جدول ترتيب المرشحين بالأرقام (المسافة، ETA، الحمل، النتيجة) — الشفافية الكاملة.
- **سجل المحادثة اللاسلكية**: نص كل ما قاله Brain وكل رد من الموصل، مع زر تشغيل الصوت.
- **مفتاح الوضع**: مراقب / مساعد / آلي + زر «تدخّل» يعيد الطلب للتحكم اليدوي.
- مؤشرات: معدل قبول العرض الأول، متوسط زمن الإسناد، عدد التصعيدات البشرية.

## 7. ترتيب البناء

1. **المرحلة 2 من الخطة** (بعد ثبات الصوت والـGPS): محرك الترشيح والترتيب + الإسناد من اللوحة يدويًا بعرض التوصية (وضع «مراقب»).
2. **المرحلة 3**: النداء الصوتي TTS + قبول بضغطة PTT (بدون STT بعد) — أبسط وأمتن حلقة كاملة.
3. **المرحلة 4**: STT + فهم النية + وضع «آلي» + اكتشاف التأخير من GPS + التصعيد الذكي.

بهذا الترتيب كل خطوة تعمل وحدها وتضيف قيمة قبل التالية، ولا نراهن على التعرف الصوتي قبل إثبات الأساسيات.
